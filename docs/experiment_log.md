# 드론 CV 파이프라인: v3 → v6 실험 기록

평가셋: 터치다운 클립 2개(0144 = ClipKey 34, 0156 = ClipKey 44)의 득점 플레이 구간에서 프레임 10장씩, 총 20장. Roboflow에서 사람이 직접 고친 정답 라벨(박스 487개, Hongik / Kookmin / Referee). 박스 매칭은 중심 거리 기준(선수가 10~25px로 작아서 IoU 대신 사용).

- v3: yolov8x, imgsz 960, conf 0.15, ByteTrack(high 0.5, low 0.15, new 0.6, buffer 40, match 0.85), RF 팀 분류기, 클립별 ROI

- **v5 (최종)**: v4 + ResNet18 팀 분류기(튜닝 클립 트랙 라벨로 전이 학습, 트랙 평균 확률) + 인원 규칙 제거 + **자동 ROI (SIFT + 호모그래피, 4a)**
- 실행 노트북: `run_v5_pipeline.ipynb` (영상 이름만 넣으면 ROI 자동 계산 → tracking_final.json + 확인용 영상, 결과는 pipeline_outputs/v5)

### 2a. 추적기 튜닝 (평가 클립이 아닌 0143 · 0157, 정답 미사용)
- 튜닝 클립 ROI: 평가 클립 ROI를 ORB 특징점 + 유사 변환으로 옮기려 했으나 실패 → 첫 프레임에서 라인 검출로 직접 계산. 0143 `[[270,459],[1880,469],[1919,612],[1919,1079],[119,1079]]`, 0157 `[[0,0],[1675,0],[1761,737],[0,733]]`
- yolo26x 1920 탐지를 한 번 캐시하고 ByteTrack 설정 55개(high×new×buffer×match + v3 설정) 비교
- 정답 없는 지표: 커버율(추적 박스 ÷ 점수 0.5 이상 탐지), ID 쪼개짐(클립별 고유 ID ÷ 프레임당 추적 인원, 가중 평균), 짧은 트랙 비율(15프레임 미만 ID)
- 사전 규칙: 쪼개짐·짧은 트랙이 v3 설정보다 10% 넘게 나빠지지 않는 설정 중 커버율 최대
- 결과: v3 설정 커버율 1.045 / 쪼개짐 1.645 / 짧은 트랙 0.034 → 선택(h0.25_n0.4_b90_m0.9) 1.082 / 1.438 / 0.037. 상위 설정이 모두 match 0.9 → 짝짓기를 느슨하게 한 것이 쪼개짐 개선의 주된 원인

### 3b. 팀 분류기 재학습 (PyTorch ResNet18)

- 적용: 평가 클립의 모든 추적 박스를 분류해 **트랙 평균 확률**로 라벨 결정

### 4a. 자동 ROI (SIFT 특징 매칭 + RANSAC 호모그래피)
- 방법: ROI를 직접 정한 프레임 4개(0144 f413, 0156 f167, 0143 f1, 0157 f1)를 참조로 등록 → 새 프레임과 SIFT 특징점 짝짓기(비율 검사 0.75, 반 해상도) → RANSAC 호모그래피(5px, 인라이어 100 미만이면 실패) → 참조 ROI를 옮김. 참조 화면 가장자리에서 잘린 ROI 변은 실제 라인 방향으로 화면 밖까지 연장한 뒤 옮김. 30프레임마다 다시 계산(드론 움직임 추적), 실패 시 직전 ROI 유지
- 사전 확인(실제 프레임, 자기 자신을 뺀 참조): IoU 0144 0.995 · 0143 0.997 · 0156 0.996 · 0157 0.996. 유사 변환도 0.993~0.995로 비슷 → 이 4개 시점은 원근 차이가 작음. 2a의 실패는 변환 모델보다 특징점(ORB)과 잘린 ROI 처리 문제였던 것으로 보임
- 실전 검증: 평가 클립 ROI를 **튜닝 클립 참조만으로** 30프레임마다 계산 (0144 22번, 0156 18번, 실패 0번)
  - 직접 ROI와 IoU: 0144 최소 0.986 / 평균 0.993, 0156 최소 0.969 / 평균 0.990 (0156의 1~121프레임이 0.97: 직접 ROI는 167프레임 기준이라 그 전의 드론 위치 차이로 추정)

- 한계: 참조가 경기장 양쪽 끝 2곳뿐이라 중앙 등 다른 곳을 찍은 영상은 실패 → 한 번 직접 입력하면 새 참조로 추가됨. 다른 경기장은 참조를 새로 만들어야 함

### 5. YOLO26 파인튜닝 (v6)
- 데이터: 튜닝 클립(0143, 0157)에서 40장 → v5 결과로 라벨 초안 → Roboflow에서 직접 수정 (박스 994개: 홍익 438 · 국민 437 · 심판 119). 평가 클립 미포함
- 전처리: 경기장 밖은 회색으로 가림(라벨 없는 벤치 인원을 배경으로 배우지 않게). 1920 원본을 640 조각(가로 4 × 세로 2, 겹침)으로 잘라 선수 크기 유지. 학습 32장 → 조각 256개, 검증 8장 → 64개
- 학습: 사전학습 yolo26m → 3클래스(Hongik / Kookmin / Referee), 60 epoch, T4 16분, 색조 증강 끔
- 평가 1, 탐지만 (평가 20장, 1920 전체 입력, conf 0.15)

| | 사전학습 yolo26x | 파인튜닝 yolo26m |
|---|---|---|
| Precision / Recall / F1 | 0.936 / 0.903 / 0.920 | 0.905 / **0.982** / **0.942** |
| FN / FP | 47 / 30 | **9** / 50 |
| 키 20px 미만 Recall | 0.312 | **0.750** |
| 속도 (T4) | 0.39초/장 | **0.16초/장** |
| 팀 정확도 (박스 단위) | 없음 | **0.987** |

- 평가 2, 추적까지 (v6 = 파인튜닝 YOLO + 2a ByteTrack + 트랙 다수결 팀, 1a ROI)

| | P | R | F1 | FP | FN | 팀 정확도 | 심판 Recall |
|---|---|---|---|---|---|---|---|
| v5 | 0.961 | 0.899 | 0.929 | 18 | 49 | 0.904 | 0.81 |
| **v6** | 0.946 | **0.969** | **0.957** | 27 | **15** | **0.922** | **1.00** |

- 해석: 직접 추가한 엉킨 선수를 학습해 작은 선수 Recall이 2배 이상. 더 작은 모델이 더 정확하고 빠름. 대가로 오탐 증가
- 팀 정확도가 박스 단위 0.987 → 추적 후 0.922로 낮아짐 (홍익↔국민 각 18건): 추적 ID가 다른 팀 선수로 넘어갈 때 트랙 전체 다수결이 오히려 틀리게 만듦 → 박스별 클래스나 짧은 구간 평균이 나을 수 있음
- conf는 평가셋을 보고 고르지 않고 사전에 정한 0.15 사용. 학습·평가가 같은 경기의 다른 장면이라 일반화는 미확인

2. **득점 선수 지표는 아직 신뢰하기 어려움**: 0156에서 v4의 ID 변경 시점(214/215, 313/314)이 v3에서 사람이 이어 붙인 구간 경계와 정확히 같음 → 정답 경로로 쓴 v3 구간(#171, #183, v3 노트북에 '추정, 확인 필요')이 실제로는 다른 선수였을 가능성. 0144의 #16 ↔ #21 전환(509~517)도 영상 확인 필요
3. 탐지 남은 FN 15, FP 27 → 학습 데이터 추가, 다른 경기로 일반화 확인
4. 자동 ROI는 같은 경기장의 참조 프레임에 의존 → 경기장 도면 좌표계로 옮기는 필드 키포인트(YOLO-Pose) + 호모그래피는 다음 단계 (연구 계획서 Step 3, 선수 위치를 야드 단위로 얻는 데도 필요)
